# 2026-09-01 — DCS parity sync

## Part 2 laradcs back-port

Back-ported the DCS defaults and behaviour from dcs.spa commit `d71aa24` into the React implementation. The shell now uses independent 15% sidebar widths with a 200px CSS floor, pins at 960px, keeps the fixed topnav above sidebars, restores desktop intent without opening sidebars on small-screen load, and persists the flat state under one configurable key.

The Appearance panel gained per-side number spinners, Narrow/Normal/Wide content modes, narrow-container reflow, and the Mono scheme. Carousel chevrons now retain direction through boundary wraps, while a one-panel sidebar omits carousel navigation. The Blade head script applies persisted visual state before Vite and leaves transition suppression in place until `ThemeProvider` completes restoration.

Documented the vendor set and consumer boundary in `_doc/2026-09-01-dcs-sync.md`. `ThemeProvider` exposes only `storageKey`, `topnavHeight`, and initial theme/scheme/per-side defaults; `config/dcs.php` supplies the matching pre-paint storage key.

## Sharp edges caught

- Responsive runtime state cannot also be the persisted desktop intent. Keeping separate saved per-side values prevents a small-screen initial render or breakpoint crossing from overwriting the user's pinned desktop state.
- React-controlled track transforms overwrite the temporary DOM transform needed for directional wrapping. The track transform is therefore effect-driven; the wrap timer suppresses transition, restores the canonical position, and clears its temporary destination offset.
- The shared legacy `sidebarWidth` key is intentionally ignored rather than migrated because the new model has two percentage values and no unambiguous conversion.
- The starter kit's separate `initializeTheme()` read an `appearance` key after the Blade script and could overwrite the pre-painted DCS class. Removing that competing initialiser keeps one theme source; a next-frame fallback in `app.tsx` removes `preload` on guest pages that do not mount `ThemeProvider`.

Browser interaction and visual behaviour were not exercised in this terminal-only session.

### Geometry REVERTED the same day (follows dcs.spa 30d7508)

The spec's "sidebars below a fixed full-width topnav" was a mistake — it was SPE's own
simplification, not a DCS default. Canonical DCS is a **three-column top row**: the fixed
sidebars' carousel headers are the outer columns (`h-[var(--topnav-height)]`, with the
3.75rem hamburger reserve on the outer side), the topnav is the in-flow centre column that
scrolls away with the content and is pushed by pinned sidebars. Restored: `Sidebar`
`fixed top-0 h-screen`; `TopNav` in flow inside the pushed wrapper (no `pt`); rail `::after`
from `top: var(--topnav-height)` animating to 0 on `body.scrolled`, with the scroll listener
back in the layout. `--sidebar-header-height` removed. Everything else from this entry stands.

Vendoring into sshm-desktop found one portability bug: `sidebar.tsx` composed
`${side}-0` at runtime, so Tailwind's scanner never saw `left-0`/`right-0` — laradcs
only got them incidentally from shadcn components, and the consumer's right sidebar
rendered at x=0. Now written as the literal ternary `side === 'left' ? 'left-0' :
'right-0'`. Rule for these files: every Tailwind class must appear as a literal
string in the file itself; a consumer has none of laradcs's other sources.

One follow-up applied: the pre-paint script hard-coded `--topnav-height: 4rem`
while `ThemeProvider` takes it as a prop, so a consumer on 3rem would get a
first-paint jump. Added `topnav_height` (`DCS_TOPNAV_HEIGHT`) to `config/dcs.php`
and read it in `app.blade.php`; documented that it must match the prop.
